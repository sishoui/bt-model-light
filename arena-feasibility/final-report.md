# 微信小程序↔单片机 BLE 交互测试 Mock/真机边界划分 可行性分析（Arena 综合版）

**判定结论：有条件可行**。原结论的核心分层（逻辑层 Mock、物理层真机）方向正确、原则成立；但完整落地存在若干未验证前提、一处边界过粗（分包时序/吞吐量）、若干遗漏测试维度，且真机矩阵承诺对轻量项目过重。裁剪为三层最小可行集后可持续执行。

> 本文由 Arena 流程综合产出：以候选 1（工程落地视角）为基准，移植候选 2（技术事实核查视角）的边界拆分与遗漏层清单；候选 2 的两处事实错误已按官方文档修正（见第五节）。

---

## 一、原结论中成立、应保留的部分

1. **核心原则成立**：Mock 覆盖逻辑正确性，真机覆盖物理正确性，两者不可互相替代。具体反例：
   - Mock 通过但真机失败：帧拼装在 mock 下按理想 MTU 一次性 write，真机上因 MTU 协商与分包，`writeBLECharacteristicValue` 可能被截断或合并，单片机收到半帧；mock 的 notify 回调即时到达，真机上 notify 可能延迟、合并或丢失；iOS CoreBluetooth 与部分 Android 厂商连续 write 时的队列与背压不同。
   - 真机跑通但逻辑不正确：端到端 happy path 只覆盖合法帧与正常时序，非法帧、校验和错误、超时、重连、状态机非法转移只有 mock 单测能系统性覆盖。
2. **Mock 小程序 JS 逻辑层可行**：无官方 BLE mock 库，需自建 `global.wx` 的 jest.fn() 集合并按回调签名实现；需覆盖回调与 Promise 两种形态；mock 只覆盖"调用顺序与参数"，不覆盖微信客户端内部的队列、MTU 协商与 notify 合并。
3. **真机集成与兼容性验证不可省**：BLE 无线链路、手机协议栈差异（iOS/Android）、单片机固件与硬件、端到端集成，只能靠真机。

## 二、必须修正的边界判定

1. **"分包时序"整体划入真机层过粗**（graft 自候选 2）。应拆为两层：
   - **JS 层拆帧/重组逻辑、缓冲与背压处理** → 可用构造好的分帧序列在 Mock 中覆盖；
   - **空口 ATT MTU 协商、notify 批量推送时序** → 只能真机 + BLE Sniffer。
2. **"吞吐量"同理拆分**（graft 自候选 2）：JS 层队列/背压处理能力可 Mock；真实 airtime 吞吐需真机。
3. **automator 不能承担 BLE 相关 UI 回归**（两候选一致，候选 2 的 CI 观察修正后采纳）：automator 只驱动 PC 开发者工具，开发者工具对蓝牙 API 仅"部分模拟"（官方文档措辞），且 automator 的系统授权弹窗需手工预授权、CLI 仅提供 macOS/Windows 路径。BLE 相关 UI 验证应改由真机 smoke test 覆盖；automator 仅保留纯 UI（页面跳转、按钮状态、setData 展示）回归。
4. **"单片机协议解析层 Mock"不是现成能力，而是有前提**（候选 1）：前提是固件把协议解析抽成纯函数（输入字节数组、输出结构体/状态、硬件副作用接口注入），且工程支持独立编译。典型轻量嵌入式 C 工程解析与寄存器、中断、定时器混写，直接不可测；未解耦时先做结构重构，成本大于测试本身。
5. **"真机测试"应区分真机调试与真机测试**（graft 自候选 2）：真机调试仍挂载开发者工具，时序与生产运行时不同，可用于链路层验证但不算发布前 QA。

## 三、原结论遗漏、必须补齐的测试维度

以下为两候选均未在原结论中覆盖、评审确认应补的项（graft 自候选 2，经评审修正）：

1. **微信权限与系统状态**：iOS 蓝牙授权弹窗、Android 12+ `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` 运行时权限、系统蓝牙关闭（errCode 10001）等权限拒绝路径只能真机触发。
2. **OTA/DFU 固件升级**：bootloader 切换、版本协商、升级失败回滚是独立链路，应单独建模。
3. **异常与生命周期**：断电/复位、小程序切后台与 `onUnload`、会话销毁后的重连策略，需真实设备与真实链路。
4. **版本矩阵**：微信基础库版本、iOS/Android 微信版本差异，是兼容性验证维度。
5. **空口可观测**：真机测试应配合 BLE Sniffer（nRF Sniffer、Ellisys 等）验证分包与重传，仅靠 App 层黑盒检查无法定位空口问题。
6. **多连接/多用户**：单片机 BLE 连接数上限与并发策略应单独建模。

## 四、对轻量项目的裁剪：最小可行集（落地基线）

原策略四层（Jest 单测、automator UI 回归、真机集成、多品牌兼容）对小程序+灯控这种轻量项目过重。裁剪为三层：

| 层 | 内容 | 工具 | 频率 | 设备 |
|---|---|---|---|---|
| 1. 逻辑单测 | 帧编解码、校验和、状态机、错误处理、JS 拆帧重组与背压 | Jest + 自建 wx mock | 每次 commit | 无（PC） |
| 2. 真机 smoke | 端到端：扫码→连接→发指令→硬件响应→回传；含权限路径 | 真机 + 真实硬件（+ 问题排查时 BLE Sniffer） | 每次发布前 | 2 台代表设备（1 iOS + 1 Android） |
| 3. UI 回归 | 纯 UI 流程（不触达 BLE） | automator | 发布前（可选） | PC 开发者工具 |

**延后项**（用户量/固件规模增长后再引入）：多品牌兼容矩阵、固件协议解析 Unity/CMock 单测（且需先完成固件解析层与硬件解耦）、HIL 台架、协议一致性/模糊测试、OTA 专项。

**CI 说明**（修正候选 2 的过度断言）：automator 依赖开发者工具 CLI 与登录，CLI 仅提供 macOS/Windows 路径——Linux 无头 runner 上不可跑，但 Windows/macOS runner（如 GitHub Actions 的 windows-latest）或本地可跑。若 CI 仅 Linux runner，则每次 commit 只能跑 Jest Mock 单测。

## 五、事实核查记录（评审结论）

1. 候选 2 称"官方文档将蓝牙相关 API 标注为模拟器不支持"——**不准确**。官方文档措辞为"开发者工具上只能模拟部分蓝牙接口能力，完整功能请使用真机调试"（部分模拟，非不支持）。候选 1 的表述与文档一致。
2. 候选 2 称"每次 commit 跑 UI 回归在 CI 中不可行"——**过度断言**，已修正为"仅 Linux runner 不可行"。
3. 两候选对"Mock 通过≠真机能跑，真机跑通≠逻辑正确"均判定成立，且给出了具体反例（MTU 截断、notify 延迟/合并、iOS/Android 背压；happy path 掩盖逻辑错误）。

## 六、最终结论

原策略**有条件可行**。保留其核心原则与分层骨架；修正四处边界判定（分包时序、吞吐量、automator 定位、单片机侧 Mock 前提）；补齐六类遗漏维度（权限、OTA、生命周期、版本矩阵、空口观测、多连接）；按最小可行集（Jest 每 commit + 2 台真机 smoke 每发布 + automator 仅 UI）裁剪后落地。核心原则一句话：**Mock 覆盖逻辑正确性，真机覆盖物理正确性，两者不可互相替代；Mock 通过不代表真机能跑，真机跑通不代表逻辑正确。**
