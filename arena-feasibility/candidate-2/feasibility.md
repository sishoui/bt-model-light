# 可行性分析 Mock 与真机的边界划分策略

**判定为有条件可行。** 原策略的主链路划分（逻辑层 Mock、物理层真机）与测试金字塔和硬件在环（HIL）实践一致，基于推理。但要落地，必须修正 3 处边界错误、补齐 4 类遗漏层，并接受工具链的平台限制。

## 1. 有误的边界判定

- **分包时序。** 原结论划入真机层。部分不成立。小程序侧的拆帧与重组逻辑可以用构造好的分帧序列在 Mock 中覆盖；真正无法 Mock 的是空口 ATT MTU 协商、手机协议栈的 notify 批量推送时序。应拆为两层。逻辑处理走 Mock，链路时序走真机。
- **吞吐量。** 同理，JS 层的缓冲、队列、背压处理能力可 Mock；真实 airtime 吞吐需真机。原结论把吞吐量整体划入真机层，丢失了可测部分。
- **UI 流程用 automator。** automator 运行在开发者工具模拟器中。据官方文档（推断，基于 API 文档对蓝牙类接口的通用说明），模拟器不支持 wx.openBluetoothAdapter 等蓝牙 API。因此 automator 只能覆盖不触达 BLE 的纯 UI 流程。本项目的 UI 全部围绕 BLE 控制，automator 无法替代真机 UI 回归。这一条站不住脚。

## 2. 遗漏的层

- **微信权限与系统状态。** iOS 蓝牙授权弹窗、Android 12 及以上 BLUETOOTH_SCAN 和 BLUETOOTH_CONNECT 运行时权限、系统蓝牙开关关闭（errCode 10001）等只能在真实设备上触发，Mock 无法验证权限拒绝路径。
- **OTA/DFU 固件升级。** bootloader 切换、版本协商、升级失败回滚是独立链路。原结论仅笼统写固件，未单独列出。
- **异常与生命周期。** 断电/复位、信号中断、小程序切后台与 onUnload、微信会话被销毁后的重连策略，均需真实设备与真实链路。
- **版本矩阵。** 微信基础库版本差异、iOS/Android 微信版本差异，是兼容性验证的维度，原结论未显式列出。
- **空口可观测手段。** 真机测试应配合 BLE Sniffer（如 nRF Sniffer、Ellisys）验证分包与重传。原结论未提及，仅靠 App 层黑盒检查无法定位空口问题。

## 3. 微信生态事实核查

- **开发者工具模拟器。** 只能模拟部分蓝牙接口这一说法可信度低（推断）。官方文档将蓝牙相关 API 标注为模拟器不支持，应以文档为准。
- **真机调试不等于真机测试。** 真机调试仍挂载开发者工具，时序与生产运行时不同。可用于链路层验证，但不算发布前 QA。
- **miniprogram-automator 在 CI。** automator 依赖开发者工具 CLI 与登录，需 Windows 或 macOS runner，无法在 Linux 无头 runner 上跑。每次 commit 跑 UI 回归在 CI 中不可行，仅能跑 Mock 单测。

## 4. 与业界成熟手段的差距

- **HIL（硬件在环）。** 原策略的真机加真实硬件是黑盒端到端，缺少 HIL 台架（PC 自动化控制手机与单片机）与协议一致性测试（conformance）、模糊测试（fuzzing）。
- **固件侧。** 协议解析层 Mock 是对的，但缺少在 PC 上对固件 C 逻辑的主机端单元测试（Unity、CMock）。
- **多连接/多用户。** 单片机 BLE 连接数限制与并发策略未单独建模。

## 5. 落地条件

1. 修正边界。逻辑处理走 Mock，空口时序与吞吐走真机加 Sniffer。
2. 补齐权限、OTA、异常、版本矩阵、多连接测试。
3. 接受 automator 仅覆盖非 BLE UI 流程。BLE 相关 UI 回归需真机或 Mock wx 层。
4. CI 仅跑 Jest Mock 单测。automator 仅在 Windows 或 macOS runner 或本地跑。

最终结论。核心原则 Mock 覆盖逻辑、真机覆盖物理 成立，策略整体有条件可行。
