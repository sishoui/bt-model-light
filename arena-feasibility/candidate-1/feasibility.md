# 微信小程序↔单片机 BLE 交互测试 Mock/真机边界划分 可行性分析

**判定结论：有条件可行**（核心分层正确，但完整落地在轻量项目中过重，若干前提未验证，需裁剪）。

## 一、整体判定依据

原结论按数据流拆分可 Mock 层与必须真机层，方向正确，符合测试分层原则。但作为"明天就落地"的工程方案，它把若干工具能力当作已具备前提，而这些前提在微信小程序与嵌入式固件生态中并不自动成立。因此整体判定为有条件可行，条件见下。

## 二、逐点分析

### 1. Mock wx BLE API 的实际可实施性

微信小程序没有官方 BLE mock 库。wx 是运行时全局对象，Jest 运行在 Node，环境中并不存在 wx。可行的落地方式是：在测试 setup 中把 global.wx 设为一个 jest.fn() 集合，并按 wx.openBluetoothAdapter、wx.writeBLECharacteristicValue、wx.onBLECharacteristicValueChange 等 API 的回调签名手工实现。这是工程上可行的，但有三个坑。

第一，wx BLE API 以回调为主，部分新 API 支持 Promise，混用时 mock 需同时覆盖两种调用形态。第二，小程序代码通常依赖微信编译器的模块化与 wx 全局，直接在 Node 下跑需要额外的转译与环境垫片，维护成本随 API 面扩大而上升。第三，mock 的价值只在"调用顺序与参数"层面，无法验证微信客户端内部的队列、MTU 协商与 notify 合并行为。

结论。可行，但需要自建并长期维护 mock 层，且 mock 只能覆盖 JS 逻辑，不能覆盖客户端协议栈。

### 2. miniprogram-automator 的实际覆盖

miniprogram-automator 只能驱动 PC 上的开发者工具，而开发者工具只能模拟部分蓝牙接口能力。因此它在本策略里不能承担"BLE 集成回归"，只能承担纯 UI 流程回归，例如页面跳转、按钮状态、表单输入、基于 setData 的状态展示。任何依赖真实 notify 回调、连接状态机与硬件响应的用例，在开发者工具里都不稳定或不可用。

结论。automator 保留为 UI 回归工具是可行的，但应从策略中移除其对 BLE 能力的隐含承诺，BLE 相关 UI 验证改由真机 smoke test 覆盖。

### 3. 单片机协议解析层 Mock 的前提

"Mock 单片机协议解析层"成立的前提是固件代码能独立编译为可运行单元测试。典型嵌入式 C 工程把协议解析与硬件寄存器访问、中断、定时器混写在同一模块里，直接不可测。要落地需要把解析逻辑抽成纯函数，输入是字节数组，输出是结构体或状态，硬件副作用通过接口注入。Unity/CMock 或 Ceedling 可以做，但它们要求工程具备可独立编译的测试目标与桩生成流程。

对于本项目这种轻量灯控，固件大概率规模小、耦合度高。结论。有条件可行。若协议解析已经与硬件隔离，则一周内可落地；若未隔离，先做结构重构，成本大于测试本身。

### 4. 真机测试的成本

真机矩阵包含 iOS 与多品牌 Android、不同蓝牙芯片与系统版本。人工执行每次回归需要设备、环境与操作步骤。把"每迭代/发布前集成验证、大版本前兼容性验证"写进策略，对小团队是持续性负担。现实可行的承诺应是：每次发布前在 2 台代表设备（1 iOS、1 Android）上跑一遍端到端 smoke test，完整矩阵仅在大版本或用户反馈问题时执行。

结论。全矩阵不可持续；缩减后的 smoke test 可持续。

### 5. "Mock 通过≠真机能跑，真机跑通≠逻辑正确" 是否成立

成立，且有具体反例。

Mock 通过但真机失败的例子。帧拼装逻辑在 mock 下按理想 MTU 一次性 write，真机上因 MTU 协商与分包，writeBLECharacteristicValue 可能被截断或合并，导致单片机收到半帧；mock 的 onBLECharacteristicValueChange 立即回调，真机上 notify 可能延迟、合并或丢失。iOS CoreBluetooth 与部分 Android 厂商在连续 write 时的队列与背压不同，mock 无法体现。

真机跑通但逻辑不正确。端到端 happy path 只覆盖合法帧与正常时序，mock 单测才能系统性覆盖非法帧、校验和错误、超时、重连、状态机非法转移。真机 smoke test 通过并不意味着这些边界被验证。

结论。这句话成立，且是本策略最值得保留的一句。

### 6. 对轻量项目的过重性与裁剪

原策略包含 Jest 单测、automator UI 回归、真机集成、多品牌兼容性四层。对小程序加灯控这种轻量项目，automator 与多品牌矩阵的投入产出比最低。建议裁剪为三层。

第一层，Jest 或等价单元测试，覆盖帧编解码、校验和、状态机与错误处理，每次 commit 运行。第二层，真机 smoke test，2 台设备，每次发布前运行。第三层，保留 automator 仅用于 UI 回归，且不承诺 BLE 能力。多品牌兼容性与 Unity 固件单测延后到固件规模或用户量增长后再引入。

## 三、裁剪后的最小可行集

- 小程序 JS 逻辑层：自建 wx mock，单元测试帧与状态机。
- 固件协议解析层：仅在解析与硬件已解耦时单测，否则延后。
- UI 回归：automator，仅 UI，不测 BLE。
- 集成与兼容性：2 台真机 smoke test，大版本前扩展矩阵。

## 四、对原结论的保留与修正

保留"Mock 覆盖逻辑正确性，真机覆盖物理正确性，两者不可互相替代"。修正三点。第一，miniprogram-automator 不应被描述为 BLE 相关验证手段。第二，"单片机协议解析层 Mock"应改为"在固件支持独立编译的前提下 Mock"。第三，真机回归频率与设备矩阵应按项目规模缩减，避免策略无法执行。
