# ADR-0008: OTA 延后 v2，但分区与命令码预留

- 状态: 已被 ADR-0034 取代（2026-11-27 落地 BLE OTA）
- 日期: 2026-11-23
- 标签: 固件

> 2026-11-27 更新：OTA 已在 ADR-0034 落地（`0xF0` 子命令 + BLE 分块 + 回滚）。
> 本 ADR 保留作决策起点记录，其中的"延后"结论不再有效；分区表与命令码预留的
> 决策仍然成立。

## 背景

OTA/DFU（bootloader 切换、版本协商、升级失败回滚）是独立链路。arena-feasibility 报告将其列为应补齐的测试维度，但对轻量灯控首版过重。

## 决策

- **首版不实现 OTA 流程**，但：
  - 分区表采用双 OTA 分区（见 ADR-0010），bootloader 从一开始规划好
  - 命令码 `0xF0` 预留给 OTA（见 ADR-0007）
  - 协议版本协商（见 ADR-0009）为未来 OTA 的"版本协商"做准备
- OTA 流程（BLE 上传 `.bin` + bootloader 切换 + 回滚）延后到 v2

## 理由

- 单片机固件首版功能优先，OTA 流程单独建模成本高
- 但 bootloader/分区一旦写死，以后切分区很痛，所以必须一开始就规划
- 命令码预留避免未来破坏协议兼容

## 影响

- 分区表 `nvs + otadata + ota_0/1 + spiffs`（见 ADR-0010）
- `0xF0` 命令码在代码生成中声明但不实现
- v2 引入 OTA 时需：实现 0xF0 命令、升级失败回滚、版本协商

## 备选

- 首版实现 OTA：对轻量项目过重，延后
- 不做 OTA 也不留 bootloader：未来切分区成本极高，不可接受
